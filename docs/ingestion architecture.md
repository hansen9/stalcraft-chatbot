|Decision|Choice|Reason|Alternative|
|--------|------|------|-----------|
|HTTP client setup|Two `@Qualifier`-disambiguated `RestClient` beans(`GithubHttpConfig`)|Tree API and raw-content API need different base URLs;separating them makes each independantly via WireMock. The fetcher have 2 phase, one to pull the GitHub Tree API and then second to do raw file fetches base on the path of the GitHub Tree API. reason for 2 phase fetching: the datas are inside subdirectories and ordered by their categories(i.e. armors, weapons, containers, etc.)|Single `RestClient` with URL-building logic scattered in the fetcher - rejected, harder to mock cleanly|
|Repo inspection method|`codeload.github.com` tarball, not the Tree API, for one-off structure verification|Tree API rate-limited; you hit two rework cycles from wrong assumptions about repo shape before adopting this|Trusting assumed structure from docs/memory - this is literally what caused the flat-array and `_variants` mistakes|
|Scope(current)|`global/items/weapon` only|Keeps ingestion fast and testable while the pipeline itself is still being built out|Ingesting all categories immediately - deferred, this is the "widen scope" item still on the roadmap|
|Realm handling|`global/` only for now, `ru/`-exclusive items deferred|confirmed realm-specific items exist in `ru/`. Scoping to `global/` first to avoid second modelling axis(which server user is on) until things are stable enough|Multi-realm ingestion from the start - explicitly deferred, not rejected|
